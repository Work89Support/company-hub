# Performance และ Load Test: Company Hub รองรับ 100 คน

วันที่ทดสอบ: 2 ตุลาคม 2026 เวลา 12:22 น. (ประเทศไทย)  
ระบบที่ทดสอบ: GitHub Pages Production และ Supabase Production (`mfvbggjwqgeaoezlgiqo`)

## ขอบเขตการทดสอบ

ทดสอบแบบอ่านข้อมูลเท่านั้น ไม่สร้างงาน ไม่แก้สถานะ และไม่เปลี่ยนข้อมูลธุรกิจ

1. ผู้ใช้จำลอง 100 คนเปิดหน้าเว็บพร้อมกัน แต่ละคนโหลดหน้า HTML และไฟล์ JavaScript/CSS หลัก 12 ไฟล์
2. ผู้ใช้จำลอง 100 คนโหลดชุดข้อมูลแดชบอร์ดพร้อมกัน คนละ 8 คำขอ รวม 800 คำขอ
3. ผู้ใช้จำลอง 100 คนเรียก Edge Function พร้อมกันด้วย CORS preflight

ไม่ได้ยิง Login จริง 100 ครั้ง เพราะระบบ Production จำกัดการลองเข้าสู่ระบบจาก IP เดียว 60 ครั้งต่อ 10 นาที การทดสอบดังกล่าวจะทำให้ทีมงานที่ใช้ IP เดียวกันถูกจำกัดการเข้าใช้ทันที

## ผลการทดสอบ

| ส่วนที่ทดสอบ | คำขอ | สำเร็จ | ผิดพลาด | p50 | p95 | p99 | Throughput |
|---|---:|---:|---:|---:|---:|---:|---:|
| หน้าเว็บและไฟล์หลัก | 1,300 | 1,300 | 0 | 61 ms | 1,989 ms | 2,338 ms | 530 req/s |
| ชุดข้อมูลแดชบอร์ด | 800 | 800 | 0 | 2,404 ms | 2,889 ms | 2,984 ms | 256 req/s |

ข้อมูลที่ส่งกลับจากหน้าเว็บรวม 278.8 MB หรือประมาณ 2.66 MB ต่อคน ส่วนชุดข้อมูลแดชบอร์ดประมาณ 8.8 MB รวม หรือ 0.08 MB ต่อคนในขอบเขตที่จำกัดไว้ 500 แถวต่อแหล่ง

## ถ้ามี 100 คนเข้าใช้พร้อมกันจะเกิดอะไรขึ้น

### 1. หน้าเว็บเปิดได้ แต่บางคนจะรอประมาณ 2–3 วินาที

GitHub Pages รองรับคำขอทั้งหมดโดยไม่พบข้อผิดพลาด แต่หน้า `index.html` มีข้อมูลและโค้ดจำนวนมากฝังอยู่ ทำให้การเข้าใช้ครั้งแรกของ 100 คนใช้แบนด์วิดท์รวมประมาณ 279 MB ผู้ใช้บนมือถือหรืออินเทอร์เน็ตช้าจะรู้สึกว่าหน้าหนักกว่าผลทดสอบนี้

### 2. หน้าแดชบอร์ดจะใช้เวลาประมาณ 3–8 วินาทีในสถานการณ์จริง

การทดสอบฐานข้อมูลแบบ 8 คำขอต่อคนให้ p95 2.9 วินาทีโดยไม่มีข้อผิดพลาด แต่หน้า Production จริงโหลดมากกว่า 8 แหล่ง พร้อมข้อมูลเต็มของงาน ผู้ใช้ เวลา ความคิดเห็น ประกาศ KPI ปัญหา และกราฟิก จึงคาดว่าหน้าหลักจริงจะอยู่ราว 3–8 วินาที และอาจนานกว่านี้เมื่อข้อมูลเพิ่มหรือใช้มือถือ

### 3. หาก 100 คนอยู่หลังอินเทอร์เน็ต/IP เดียว จะมีอย่างน้อย 40 คนเข้าไม่ได้ในรอบแรก

Edge Function นับคำขอ Login ตาม IP ก่อนตรวจรหัสผ่าน และจำกัดที่ 60 ครั้งต่อ 10 นาที ดังนั้นสำนักงานที่ออกอินเทอร์เน็ตผ่าน Public IP เดียวมีโอกาสที่ผู้ใช้คนที่ 61–100 ได้รับ `429` แม้กรอกข้อมูลถูกต้อง ปัญหานี้เป็นข้อจำกัดจากกฎป้องกันการเดารหัส ไม่ใช่กำลังของฐานข้อมูล

### 4. การอนุมัติเครื่องจะเป็นคอขวดด้านการปฏิบัติงาน

บัญชีพนักงานเปิดบังคับตรวจเครื่อง หาก 100 คนเข้าครั้งแรกพร้อมกัน จะเกิดคิวอนุมัติเครื่องจำนวนมาก ผู้ดูแลต้องอนุมัติก่อนที่พนักงานจะเปิดข้อมูลงานได้ จึงควรทยอยให้เข้าทดสอบก่อนวันเปิดจริง

### 5. Realtime ต้องตรวจโควตาแผน Supabase เพิ่ม

หน้าเว็บเปิดหลาย Realtime channel สำหรับงาน กราฟิก Action Tracker และข้อมูลรายงาน การทดสอบครั้งนี้ยืนยัน HTTP/API แต่ยังไม่ได้ยืนยันจำนวน WebSocket connection และ message quota ของแผน Supabase ปัจจุบัน

## ผลตัดสิน

สถานะ: **ผ่านด้านโครงสร้างพื้นฐานแบบอ่านข้อมูล แต่ยังไม่พร้อมให้ 100 คนล็อกอินพร้อมกันจาก IP เดียว**

- GitHub Pages: ผ่าน
- Supabase read workload 100 คน: ผ่าน แต่ p95 สูงและต้องลดจำนวนคำขอ
- Edge Function: ผ่านด้านการตอบกลับ
- Login 100 คน: ไม่ผ่านตามค่าจำกัดปัจจุบัน 60 ครั้งต่อ IP ต่อ 10 นาที
- First-login/device approval: ต้องทยอยเปิดเป็นรอบ

## สิ่งที่ควรแก้ก่อนเปิด 100 คน

1. ปรับ rate limit ของ IP สำหรับ Login ให้รองรับสำนักงานหลัง NAT เช่น 300 ครั้งต่อ 10 นาที พร้อมคงขีดจำกัดชื่อผู้ใช้ไว้ 12 ครั้ง เพื่อยังป้องกันการเดารหัสรายบัญชี
2. แยกการนับ Login สำเร็จออกจาก Login ผิด เพื่อลดการบล็อกผู้ใช้จริงช่วงเปิดระบบ
3. ย้ายข้อมูลตัวอย่าง/ประวัติขนาดใหญ่ออกจาก `index.html` และเปิดใช้การบีบอัดหรือ lazy loading เพื่อลด 2.66 MB ต่อคน
4. เปลี่ยนหน้าแดชบอร์ดให้เรียก summary endpoint หรือ database view แทนการโหลดตารางเต็มหลายชุด
5. จำกัดข้อมูลตามแผนกและช่วงวันที่ตั้งแต่ฝั่งฐานข้อมูล พร้อม pagination สำหรับงาน ความคิดเห็น ปัญหา และกราฟิก
6. ทยอยให้พนักงานเข้า 20–25 คนต่อรอบเพื่อเปลี่ยนรหัสและอนุมัติเครื่องก่อนวันเปิดเต็มระบบ
7. ตรวจ Supabase plan quota สำหรับ Realtime concurrent connections, egress และ database compute ก่อนเปิดครบ 100 คน
