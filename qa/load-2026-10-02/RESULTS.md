# Performance และ Load Test: Company Hub รองรับ 100 คน

วันที่ทดสอบ: 2 ตุลาคม 2026
ระบบที่ทดสอบ: GitHub Pages Production และ Supabase Production (`mfvbggjwqgeaoezlgiqo`)

## ขอบเขต

ทดสอบ Production แบบอ่านข้อมูลเท่านั้น ไม่สร้างงาน ไม่เปลี่ยนสถานะ และไม่แก้ข้อมูลธุรกิจ

1. ผู้ใช้จำลอง 100 คนเปิดหน้าเว็บพร้อมกัน โดยโหลด HTML และไฟล์ JavaScript/CSS หลักคนละ 13 คำขอ
2. ผู้ใช้จำลอง 100 คนโหลดข้อมูลแดชบอร์ดพร้อมกัน คนละ 8 คำขอ รวม 800 คำขอ
3. ผู้ใช้จำลอง 100 คนเรียก CORS preflight ของ Edge Function พร้อมกัน

ไม่ยิงรหัสผ่านของพนักงานจริง 100 บัญชี การยืนยันพฤติกรรม Login ใช้ automated test ของ Edge Function เพื่อไม่รบกวนบัญชีและคิวอนุมัติเครื่องใน Production

## สิ่งที่แก้ไข

- Login สำเร็จไม่เพิ่มตัวนับความล้มเหลวของ IP อีกต่อไป
- รองรับสำนักงานที่ผู้ใช้แชร์ Public IP เดียวกันได้สูงสุด 300 ความพยายามล้มเหลวต่อ 10 นาที และยังจำกัดรายชื่อผู้ใช้ไว้ 12 ครั้ง
- ตรวจตัวนับก่อนเรียก Auth และล้างตัวนับรายชื่อเมื่อ Login สำเร็จ
- โหลดข้อมูลหลักและ Graphic พร้อมกัน และโหลดกลุ่มข้อมูลแดชบอร์ดแบบขนาน
- ย้ายภาพคู่มือขนาดประมาณ 1.19 MB ออกจาก `index.html` ไปเป็น `manual-images.json` ซึ่งจะโหลดเมื่อผู้ใช้เปิดคู่มือ

ผลสำคัญ:

- หน้าเว็บ Production ตอบครบ 100% ทั้งสองรอบ
- ปริมาณข้อมูลเข้าใช้ครั้งแรกลดจาก 278.8 MB เหลือ 159.7 MB หรือลดประมาณ **42.7%** สำหรับผู้ใช้ 100 คน
- p95 ของไฟล์หน้าเว็บลดจาก 1,989 ms เหลือ 1,213 ms หรือดีขึ้นประมาณ **39.0%**
- คำขอฐานข้อมูลสำเร็จ 100% แต่รอบหลังช้ากว่ารอบแรก จึงยังไม่ควรสรุปว่าฐานข้อมูลเร็วขึ้นจากการวัดเพียงสองรอบ ความเปลี่ยนแปลงของหน้าเว็บช่วยลดเวลารวมจากการรอแบบลำดับ แต่ synthetic database bundle เรียก 8 แหล่งพร้อมกันอยู่แล้ว
- Edge Function ตอบครบ 100% และกฎ Login ใหม่ผ่าน automated regression test

## ผลตัดสิน

สถานะ: **พร้อมสำหรับผู้ใช้ประมาณ 100 คนในงานอ่านและใช้งานทั่วไป โดยควรทยอย First Login/อนุมัติเครื่อง และเฝ้าดูฐานข้อมูลในวันเปิดจริง**

- GitHub Pages: ผ่าน ไม่มีคำขอผิดพลาด และ payload หน้าแรกลดลงชัดเจน
- Supabase read workload: ผ่าน 800/800 คำขอ แต่ p95 รอบหลัง 3.84 วินาที ควรติดตาม Database CPU/connection และ query latency ในวันเปิด
- Edge Function: deploy แล้ว และ preflight ผ่าน 100/100
- Login หลัง NAT: แก้กฎแล้ว ผู้ใช้ที่ Login สำเร็จไม่กินโควตา IP ร่วม
- First-login/device approval: ยังต้องดำเนินการเป็นรอบ เพราะเป็นคิวงานของผู้ดูแล ไม่ใช่ข้อจำกัดของหน้าเว็บ
- Realtime และการเขียนพร้อมกัน 100 รายการ: ยังไม่ได้ยิงใส่ข้อมูล Production เพื่อหลีกเลี่ยงการสร้างข้อมูลทดสอบและแจ้งเตือนจริง

## แผนเปิดใช้ 100 คน

1. ให้พนักงาน First Login และขออนุมัติเครื่องเป็นรอบละ 20–25 คน
2. มีผู้ดูแลอนุมัติเครื่องอย่างน้อย 1 คน และผู้ดูแลข้อมูล/การใช้งานอย่างน้อย 1 คน
3. วันเปิดจริงตรวจ Supabase Database CPU, connections, API latency, Realtime connections และ egress ทุก 15 นาทีในชั่วโมงแรก
4. หากหน้า Dashboard p95 เกิน 5 วินาทีต่อเนื่อง ให้ลดช่วงวันที่เริ่มต้น เพิ่ม pagination และสร้าง summary view/RPC สำหรับการ์ดสรุป
5. ทดสอบการเขียน 100 รายการและ Realtime ใน staging หรือบัญชีทดสอบแยกก่อนนำผลไปยืนยันความสามารถด้าน write concurrency
